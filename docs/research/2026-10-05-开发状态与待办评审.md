# 2026-10-05 开发状态与待办评审

> 本文是 v0.3.0 发布后的当前状态基线。它把“代码存在”“自动化验证通过”“真实宿主验证通过”“可对外承诺”分开记录，供后续开发、真机验收和发版使用。
> 核对范围：源码、测试、构建配置、发布包、README/ROADMAP/MODULES/FAQ/隐私文档、GitHub 元数据和真机批手册。
> 核对日期：2026-10-05（Asia/Shanghai）。

## 1. 当前结论

小驴管家已经过了“功能骨架验证”阶段，进入“发布信任和真实使用闭环”阶段。

- **版本状态**：v0.3.0 已创建 GitHub Release，package.json、根 plugin.json、README 和 CHANGELOG 已使用 0.3.0。
- **生产功能**：已具备四个生产 Tab、31 个 schema 目录、按需建库、提醒中枢、成员管理、CSV/ICS/VCF/JSON 等可携带能力、附件/资源字段、健康诊断和部分兄弟插件桥接。
- **自动化质量**：pnpm test 当前为 30 个测试文件、250 项通过；类型检查、i18n、元数据和生产依赖审计通过；生产构建通过。
- **活体边界**：活体套件验证了内核读写、分页、删行、资源/附件和部分提醒路径，但不等于 Svelte UI、移动 WebView、读屏、主题和用户流程已通过。
- **发布阻塞**：真实 SiYuan UI 六阶段真机批尚未执行；icon.png、preview.png 仍是占位素材；GitHub Release 工作流的自动门禁少于发布清单要求。
- **当前不应宣传**：31 个 schema 不等于 31 个完整业务模块；代码里存在的生态桥不等于已完成兄弟插件互测；本地优先不等于自动备份；浏览器原型不等于移动端支持。

当前开发目标应从“继续增加模块数量”切换为：

> **让用户在 5 分钟内完成：成员 → 第一条证件/事项 → 看懂提醒 → 回到原始依据继续办理，并且在失败、重装、导出和恢复时知道发生了什么。**

## 2. 能力证据分层

后续 README、集市说明、CHANGELOG 和 issue 回复统一使用以下四级，不再用“已实现”一个词覆盖所有状态。

| 等级 | 含义 | 当前证据 |
|---|---|---|
| L0 规划 | 只有研究、原型或待办，没有生产路径 | TODO.md §35–62、prototype/、docs/design/ 候选页 |
| L1 代码存在 | 生产源码或 manifest 有入口，未完成端到端验证 | 生态桥、部分模块 schema、部分前端声明 |
| L2 自动化/内核验证 | 单测、构建或活体内核路径通过，仍未证明宿主 UI | 250 项单测、tests/live/、docs/testing/v0.2.md §8 |
| L3 用户可承诺 | 真实 SiYuan 宿主、目标前端/设备、成功与失败恢复路径均有记录 | 需完成 device-batch-runbook.md 六阶段并回填证据 |

对外能力表建议增加列：schema / 建库 / capture / 读写 / provider / reminder / export / mobile / evidence。
模块状态建议只使用：ready、partial、schema-only、planned、untested。

## 5. 建议开发顺序

### 阶段 A：信任门禁（先做，预计 1–2 个开发波）

1. 版本单源与诊断显示修复。
2. 跨平台 smoke 修复。
3. ROADMAP/MODULES/release checklist/privacy/FAQ 事实同步。
4. Release tag 增加 test/smoke/package manifest/size gate。
5. 修正共享、同步、备份、无网络绝对表述。
6. 建立能力证据矩阵和兼容矩阵。

**阶段出口**：任意开发环境可复现检查；版本不会漂移；发布包可在 Windows/Ubuntu/macOS 自证；对外文案不超过证据。

### 阶段 B：真实宿主验收（上架前唯一硬闸门）

依照 docs/testing/device-batch-runbook.md：

1. 首启、跳过、失败重试、缺库重建。
2. 四页主路径、详情抽屉、导入导出、设置事务。
3. 键盘、触屏、软键盘、返回、旋转、浅深主题、forced-colors。
4. Android/iOS/桌面/浏览器/独立窗口兼容矩阵。
5. 兄弟插件互测、多设备冲突、前后台/锁屏/跨天。
6. 200/500/1000 行和低端设备资源记录。
7. 真实生产截图、preview 和 social preview。

**阶段出口**：docs/testing/v0.2.md 清单有结果和证据链接；失败项有已知问题与用户可执行恢复方式；集市上架是否开启再单独决策。

### 阶段 C：首条价值闭环

按真实验收结果，只选择 3–5 个用户结果：

1. 首条记录和提醒回执。
2. 失败保留输入与重试。
3. 缺库/误删/成员悬空关系的恢复。
4. 移动端最常用动作的可发现性。
5. 导出、备份、恢复的可理解性。

每项必须同时有源码/单测、桌面宿主、真实移动、失败恢复和文档/截图证据。

### 阶段 D：观察池

拼音检索、已有块绑定、Webhook、rollup、双日期、QR、语音、AI、家庭共享权限、更多模块深化全部留在研究池。只有在阶段 B/C 产生真实需求和停止条件后进入版本承诺。一个版本最多承诺 3–5 个用户可验证结果。

## 6. 明确暂缓与不重复立项

- 不把浏览器窄视口当成移动验收。
- 不把 schema 数量当成完整模块数。
- 不把活体内核测试当成 UI 通过。
- 不因为已有 API 就承诺思源尚未公开稳定的 Agent/权限/推送能力。
- 虚拟滚动只有在真实数据量和帧率达到阈值后再做。
- 时刻/重复语法解析先不扩展快速录入日期语义。
- AI 自动归类、语音入口和家庭共享权限系统待宿主能力、隐私和真实需求验证。
- 集市上架继续保持暂缓，直到阶段 B 通过。

## 7. 后续维护规则

- 每个待办必须有：编号、主责文件/模块、依赖、用户结果、关闭证据、停止条件。
- 历史波次只用于追溯，不作为当前完成率或队列。
- 文档中的版本、测试数量、兼容性、截图和状态一律注明核对日期；能自动生成就不手写。
- 任何“已完成”必须注明证据等级 L1/L2/L3；没有真实宿主证据时写“待真机验证”。
- 新功能先进入本评审文档的阶段 C 或观察池，再决定是否新增 TODO.md 编号，避免形成平行清单。
