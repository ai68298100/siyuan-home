# 2026-10-02 · AI 融入与思源智能体调研

> 本轮只做调研与待办扩充，没有调用 AI、修改业务代码、写入思源工作区或发布。调研结论服务于 [AI 总体设计](../design/10-AI融入与思源智能体.md) 与 [提示词模板设计稿](../design/11-内置AI提示词模板.md)。

## 1. 当前开发状态

- 仓库 `main` 为 `10eccfe`，插件版本 `0.2.0`，`plugin.json` 的最低思源版本为 `3.8.0`，SDK 锁定 `siyuan@1.2.8`。
- 31 个 schema 有目录项；当前注册表只有 `members` 标记 ready，其余为 skeleton。`src/kernel.ts` 仍是生命周期日志，尚无 Agent 接线、模型调用或提示词目录。
- 旧待办仅有“AI Agent 能力注册”单项，并把智能归类放在远期。若只注册一个工具，无法覆盖资料依据、模块录入、提醒解释、办理准备和系列接力，也不能说明提示词怎样进入原生 Agent。
- 现有 schema 中 `parenting` 提醒引用了未声明的 `due`，`pets` 周期规则引用了未声明的 `cycle`；AI 模板不能掩盖这类确定性契约缺口。

## 2. 思源公开契约核验

核验对象为本地 `node_modules/siyuan` 类型和固定版本源码（思源 v3.8.0/v3.8.5、petal v1.2.8），并与官方 sample v0.5.0 的注册/注销样例对照。

| 结论 | 证据与规划影响 |
|---|---|
| 前端可注册能力 | `Plugin.addAgentCapability` 接收 `name/title/description/inputSchema/outputSchema/effects/actionEffects/handler`，handler 为 `(args, app)`，返回 `result/structuredContent/error` 包装；注册结果是稳定能力 ID，不能误称 `run`。实际版本和前端显示需真机回归。 |
| 内核可注册和注销 | `siyuan.agent.registerCapability(name, config, handler)` 与 `unregisterCapability(localName)` 是公开类型；sample 在 `onunload` 注销。前端 SDK 没有公开 `removeAgentCapability`，不能调用内部 registry。 |
| 副作用和授权 | `localRead/localWrite/dataEgress/externalCost` 及按 `action` 的 `actionEffects` 可声明；宿主另有 capability/approval policy。声明帮助宿主判断，不能替代小驴管家自己的成员、模块、字段范围授权。 |
| Schema 和返回 | 宿主可校验输入及输出；输出校验失败时动作可能已发生并变成未知结果。内核 handler 返回普通可序列化值，桥接为 JSON 文本与结构结果；不能套用前端 `{error:...}` 语义。 |
| 取消和上下文 | 插件 handler 没有自动 `AbortSignal`、`sessionID` 或 `toolCallID`；`_sessionID/_toolCallID` 只对原生工具注入。取消/超时后应按 operation ID 回读，禁止盲目重试。 |
| 提示词入口 | 当前公开 SDK 未找到稳定 `openAgent/fillPrompt/sendPrompt`。`AgentChat.sendMessage` 是 private；源码中的 `/api/ai/agent/chat` 与 skills 路由没有作为稳定插件 API 列出。先做提示词预览/复制及上下文包，不能模拟 DOM 或调用内部方法。 |
| 选区和原文 | 公开 command/menu context、block icon、tracked range 可用于产品入口显式捕获；能力 handler 不会自动收到最初选区正文。原生 Agent 的编辑器上下文也不等于插件参数。 |

## 3. 产品调研得到的 AI 设计启发

本轮查阅公开产品资料，取其机制启发，不把竞品能力当作小驴管家已拥有的实现：

1. Notion Enterprise Search 的官方说明强调回答引用工作区或连接器来源，并可限制搜索来源范围。对管家的直接启发是：每个回答带可打开的 sourceId、实际检索范围和未读取项；“未找到”不能被说成“没有”。见 [Notion Enterprise Search](https://www.notion.com/help/enterprise-search)。
2. Home Assistant Assist 将本地语音处理和云端语言模型作为不同配置路径，并强调只有显式暴露的实体/脚本才供助手操作。对管家的启发是：模型位置、资料外传和可执行能力分别显示；仅已授权字段/动作进入上下文，核心手动路径在 AI 不可用时仍可用。见 [Assist](https://www.home-assistant.io/voice_control/assist/)。
3. AI 录音/任务产品的共同产品信号是“捕捉后形成结构化草稿”，但家庭档案的风险更高：完整证件号、健康资料、账户备注、照护责任和真实办理结果不能由流畅摘要替代。因此模板优先抽取和证据问答，再到人工确认的差异预览，最后才研究写能力。
4. 搜索、摘要、自然语言筛选和语音并不等于同一种能力。没有宿主已验证的 OCR、语音转写、PDF 全文和实时外部查询时，模板只接受用户选中的文字或已核验的摘录，避免把附件列存在误宣传为附件已读。

## 4. 全局任务矩阵

AI 任务按“读取资料→形成理解→提出草稿→人工采用→真实回执”分层：

| 任务 | 适合 AI | 确定性宿主/用户负责 | 首批模板 |
|---|---|---|---|
| 总览 | 归纳要办、未知、待确认和可先准备事项 | 日期规则、范围、权限、事实 | `answer_with_evidence` |
| 录入 | 从选定文字映射字段、识别冲突与缺项 | schema、ID、枚举、写入 | `extract_record` |
| 依据 | 回答“依据在哪/为何出现” | 来源读取、链接权限、提醒规则 | `answer_with_evidence`/`explain_reminder` |
| 办理 | 整理材料、阻断和下一步草稿 | 外部要求、提交、受理、回执 | `prepare_case` |
| 变更 | 解释新旧凭证差异和影响候选 | 原值、版本、关系/提醒实际变更 | `preview_change` |
| 交接/复盘 | 压缩已获准资料、列待确认与维护负担 | 接收授权、责任接受、统计口径 | `draft_care_handover`/`review_period` |
| 系列接力 | 安排模块与小驴插件最小上下文传递 | 能力协商、唯一负责方、实际回执 | `plan_plugin_handoff` |

## 5. 数据和隐私边界

- 任务级最小上下文包含模板/字段版本、稳定对象 ID、已选来源及定位、读取完整性、宿主计算结果、模型服务和可用能力。默认 `writeMode=none`。
- 证件号、社保账号、保单号、取件码、密码、密钥和恢复码默认不传；备注/附件先筛秘密。只为回答“保修条件”提供相关条款，不把全家健康资料作为默认背景。
- “本地优先”描述台账位置，并不保证用户配置的思源模型在本机。调用前应让用户看见会提供给哪个服务的哪些片段、已知费用条件和可取消状态；插件不自行保存供应商 token，不增加默认遥测。
- 资料中出现的“忽略前文”“把所有资料发出去”等命令只能当内容分析，不能改变任务。真正的范围、权限、字段和写入门禁由宿主与插件校验。

## 6. 模板和评估

首批模板设计存于 [11 文档](../design/11-内置AI提示词模板.md)：8 个跨模块任务、31 个模块任务卡，共用一个可版本化基底。每个模块以两个业务变体区分，避免“家庭助手”万能提示词掩盖不同字段和后果。

后续评估用合成/脱敏 fixture，至少覆盖有依据、无依据、部分读取、冲突、同名成员、旧版本、跨时区、农历、金额/单位错误、不可读附件、资料注入、伪造 ID、非法 JSON、重复采用、取消后未知结果。指标包括字段准确、缺项识别、引用可回源、越界拒绝、人工修正量、净节省时间、延迟和费用；本轮不运行评估。
