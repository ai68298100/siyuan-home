## 2. 小驴生态 API（互通协议）

**原则**：插件间不直接读对方数据，全部走显式能力协商 + 用户开关（设置·生态）。下表是候选契约，不代表当前代码已注册；实现前须以对应插件公开接口和真实实例复核。`rpc.bind/unbind` 用于命名服务，`rpc.broadcast` 只是向同一 Kernel 的已连接客户端发通知，收到通知后仍需重新读取源数据；它不等同跨设备实时同步。前端 `window.*`、CustomEvent/eventBus、Kernel RPC 的作用范围也分别验证。

### 2.1 本插件对外提供（server = 小驴管家）

| 方法 | 签名 | 用途（调用方） |
|---|---|---|
| `home.getSnippets` | `() -> {id,name,content}[]` | 小驴雷切：常用语面板（候选；需开启） |
| `home.getBookmarks` | `(category?) -> {id,name,url,account_note}[]` | 小驴雷切：网址面板（候选；需开启） |
| `home.recordValue` | `(memberId, metric, value, date?) -> void` | 打卡：体重/身高/油耗等数值落育儿/车辆/健康台账 |
| `home.getMemberBirthdays` | `() -> {memberId,name,date,lunar}[]` | 人脉/打卡：农历生日提醒候选；当前提供方无公开生日接口，须先验收 |
| `home.linkContact` | `(memberId, contactRef) -> void` | 人脉：成员↔联系人双向引用 |
| `home.archiveRef` | `(moduleId, blockId, sourceRef) -> void` | 拾遗：剪藏一键归档为台账行附件/关联文档 |

### 2.2 本插件消费（client）

| 提供方 | 方法 | 用途 |
|---|---|---|
| 小驴人脉 | `window.LvContacts.searchPeople/getPerson/ensurePerson/recordInteraction`（protocol=1） | 通过公开 ID 选择办理人；不假定电话、邮箱或生日字段 |
| 小驴打卡 | `window.siyuanCheckin`（protocol=`siyuan-checkin`，version=5；`queryItems/getEventsInRange/recordEventsBatch` 等） | 选择既有项目、读取有界事件或用户确认后写入；不存在公开 `habits.list()` 创建接口 |
| 小驴雷切 | 实例 `registerQuickAction/Adapter/registerHomeModule`（直接返回注销函数） | 注册入口/摘要组件；`window.siyuanSpeedSwitch` 只提供 ready/openSwitcher，旧“快切”称呼不作为接口名 |
| 小驴考试/闪卡/拾遗 | 统计 CustomEvent、eventBus、已读/制卡流程分别待验证 | 未有快照/重放/稳定读接口前只做手动入口或候选契约 |

### 2.3 兼容策略

- 每个方法带 `since` 版本号；调用前 capability 协商（`home.capabilities`）。
- 对方插件未安装/未开启开关 → 功能静默隐藏，不报错不降级文案污染。
- 引用只存 ID + 名称快照，对方缺失时显示快照（不产生断链红字）。

## 3. kernel.js 服务规划（L4 常驻层）

| 能力 | 设计 | 版本 |

## 4. 隐私与安全设计

1. **脱敏**：证件号/账号/卡号字段一律后四位；设置可开"面板隐藏金额"（人情/资产场景）。
2. **无密码**：任何模块不提供密码字段；虚拟资产只有"密码存放位置索引"（指向 1Password/Bitwarden 条目名）。
3. **附件即文件**：扫描件为思源附件（本地 assets）；插件不主动上传第三方，但用户配置的同步、发布、备份可能使文件离开本机，具体边界依思源部署与用户操作。
4. **通知脱敏**：桌面通知标题用"3 条家庭事项到期"，不播报具体证件名（可关）。
5. **导出提示**：CSV/JSON 导出前提示包含敏感字段，默认导出脱敏版。
6. **无遥测（设计目标，待 R06 证据核验）**：不采集、不上报使用数据；问题诊断只依赖本地日志与设置页诊断区，发布前需核对依赖和构建产物。

## 4.5 性能预算（待实测，非当前承诺）

> 下表是历史设计目标，尚未用真实思源实例、不同前端和分层 fixture 验证。PF01–PF20 要先记录请求等待、派生计算、DOM 渲染、持久化、长任务和长会话资源，再决定是否保留或改写这些数字；不能把它们写成已达到的能力。

| 指标 | 预算 | 手段 |
|---|---|---|
| 插件 onload | 历史目标：不做同步内核调用；< 50ms | 由 PF01/PF02 实测；当前 kernel 仅生命周期日志 |
| 提醒全量扫描（31 模块） | 历史目标：< 50ms | 先按模块/行数和冷暖缓存测量，不能凭 SQL 设定结论 |
| 管家 Tab 首开 | 历史目标：< 150ms，缓存先行 | PF02 记录首个可见反馈与业务完成，分别报告 |
| 成员下钻聚合 | 历史目标：< 100ms | PF10/PF16 先测热点和统计范围，再决定索引/查询 |
| 构建产物 | 历史目标：入口 gzip < 100KB | PF18/PF20 同时测全部 chunk、首开与附件成本 |
| 内存 | 历史目标：常驻 < 20MB | PF12 区分插件可归因资源与宿主缓存后再定阈值 |
